# Exploration 10: Final Synthesis and Design Specification

## Direction

Consolidate E1–E9 into a single actionable design specification. This
is not a new exploration — it's the distillation. For each component,
state the decision, the rationale (which exploration proved it), and
the remaining open questions. The goal: a document someone could use to
start implementing.

---

## The Core Model: Program as Contract

**Decision**: The computation WASM IS the spending condition. The hash
of the WASM binary is the contract hash. No separate computation request
or result types.

**Source**: E4, validated by E5, E8, E9.

**What this means concretely**:

An output `{ contract: H, value: V, data: D }` is claimable by any
block that runs the WASM program identified by hash H, passes the
program the output data D as input, and produces output data that the
program accepts. Verification = re-execution with the same inputs.

**Self-perpetuating chains**: When the computation produces an output
with the same contract hash H, the chain continues:

```
output(H, state_0) → [block runs H] → output(H, state_1) → [block runs H] → ...
```

Each link is independently verifiable. No special chain mechanism.

**Result convention**: The first output on the claiming block whose
contract hash matches the claimed output's contract hash is the result.

## WASM Interface

**Decision**: Minimal export interface with auto-generated verification.

**Source**: E4, refined by E9.

### Required Export

```
compute(input_ptr, input_len) → (output_ptr, output_len)
```

The host calls `compute()` with the concatenated input data. The
function produces output data via host function calls and terminates
with `accept()` or `reject()`.

### Host Functions (importable by WASM)

```
output_data(ptr, len) → void           // emit an output's data
block_output_data(index) → (ptr, len)  // read a claimed output's data
accept() → void                        // computation succeeded
reject() → void                        // spending condition not met
```

### Optional Exports

```
weight() → u64                         // declared computation weight
list(data, path) → keys                // explorer: list children
read(data, path) → bytes               // explorer: read value
type(data, path) → type_tag            // explorer: value type
validate(root, path, proof) → bool     // offline state: validate proof
finalize(state) → migration_data       // versioning: prepare migration
```

### Verification

Auto-generated by the host: re-execute `compute()` with the same inputs,
compare output. No developer-written verification code.

## The Deception Game

**Decision**: Self-catching insurance commitments on FOR collateral blocks.

**Source**: E2, parameters refined by E7.

### Mechanics

1. Every publisher publishes an insurance commitment:
   `HASH(correct_result || 256-bit-secret)` as an output on their FOR
   collateral block.

2. If the result is intentionally wrong (a trap):
   - A verifier who re-executes and finds a mismatch can challenge,
     claiming the publisher's FOR collateral.
   - If no one catches it within the deadline, the publisher reveals
     the secret and correct result, claiming the aggregator's collateral
     (the jackpot).

3. Universal insurance: all publishers commit, making traps
   indistinguishable from honest blocks.

### Equilibrium Parameters

From E7's analysis with concrete protocol constants:

```
c = W × COLLATERAL_PER_WEIGHT       (publisher's loss when caught)
j = W × N                           (jackpot from self-catch)
b = bounty                          (honest reward)

j/c = N / COLLATERAL_PER_WEIGHT

Target: N = 1,000, COLLATERAL_PER_WEIGHT = 10
→ j/c = 100
→ equilibrium catch rate ≈ 99%
→ equilibrium fraud rate ≈ 1%
```

### Privacy Non-Issue (E5)

By the time a verifier can check the insurance commitment, they've
already re-executed and know the answer. The 256-bit secret is
sufficient.

## Weight and Gas

**Decision**: Hybrid weight model with gas-limited execution.

**Source**: E7, building on E5.

### Gas Budget

```
gas_limit = declaredWeight × INSTRUCTIONS_PER_WEIGHT_UNIT
INSTRUCTIONS_PER_WEIGHT_UNIT = 1,000,000  (1M instructions per weight unit)
```

Exceeding the gas limit = invalid block (same as wrong output).

### Consensus Weight

```
consensus_weight = computation_weight + economic_weight

computation_weight = declaredWeight
economic_weight = sum(output_values) × WEIGHT_PER_VALUE
```

Only computation_weight determines the gas budget. Economic weight is
structurally verifiable.

### Verified Weight

The sampling module observes actual gas consumed during re-execution:

```
verified_computation_weight = (actual_gas / gas_limit) × declaredWeight
```

This prevents weight inflation through gas overpayment.

### Collateral

```
required_collateral = consensus_weight × COLLATERAL_PER_WEIGHT
COLLATERAL_PER_WEIGHT = 10
```

### Gas Cost Schedule

```
WASM instruction:        1 gas
output_data(bytes):      100 + len(bytes) gas
block_output_data(i):    200 gas
memory page allocation:  1,000 gas
```

## Challenges and Offline State

**Decision**: Challenges and queries are SEPARATE primitives. Challenged
≠ invalid.

**Source**: E3, validated by E5.

### Challenges

- Adversarial: challenger stakes collateral.
- Affect validity: undefended challenge → block treated as fraudulent.
- Anti-spam: challenger loses stake if publisher responds correctly.
- Rate-limited: max K pending challenges per block.
- Stake: contract-declared via `challenge_cost()` export, with protocol
  minimum fallback.

### Queries

- Cooperative: requester posts bounty.
- No validity impact: unanswered query just means lost bounty.
- Can escalate to challenge if response is invalid.

### Validity Lifecycle

```
PRESUMED_VALID → CHALLENGED → DEFENDED or FRAUDULENT
```

Aggregators should not aggregate blocks with pending challenges
(rational economic choice, not protocol rule).

### Offline State Commitments

Outputs carry a merkle root + schema WASM hash. The schema WASM exports
`validate(root, path, proof) → bool`. Actual data lives with the
publisher. Challenge-response verifies specific paths.

### Aggregation Options for Offline State

1. **Carry forward**: Cheap. Publisher keeps custody. Aggregation block
   references the commitment.
2. **Absorb**: Expensive. Aggregator takes custody and inlines the data.
3. **Inline**: For small state. Data is stored directly in the output.

## Computation Chains

**Decision**: Self-perpetuating chains through UTXO claims with chain-
aware sampling and aggregation-as-checkpointing.

**Source**: E4 (mechanism), E6 (dynamics).

### Chain Mechanics

```
output(H, state_N) → [claim + compute] → output(H, state_N+1) → ...
```

Each link is a separate block, independently verifiable.

### Cascade Handling

A trap at link K invalidates all downstream blocks. When caught:

1. Downstream blocks become non-canonical.
2. Innocent publishers get collateral returned (non-canonical reclaim).
3. Requesters lose bounties.
4. Chain rewinds to last valid state.

**Cascade depth bounded by aggregation frequency.** Aggregation =
checkpoint.

### Sampling Module Adjustment

Chain head blocks get a priority boost to counteract descendant
dampening:

```
chain_boost(block) =
  if block is chain head AND has unverified chain descendants:
    log(descendant_chain_length)
  else:
    0

priority(T) = swing × dampening × (1 + chain_boost) / sqrt(verification_cost)
```

### Aggregator Behavior

Aggregators should verify chain blocks more thoroughly before
aggregating. Full re-execution of chain segments, not just statistical
sampling. The aggregation fee should reflect this cost.

## Contract Versioning

**Decision**: Explicit migration through FINALIZE + MIGRATION_READY.
Immutability is a feature.

**Source**: E8.

### Migration Flow

1. V1 contract includes a FINALIZE mode that produces a MIGRATION_READY
   output.
2. Developer writes V2 WASM and a migration WASM.
3. Migration block claims MIGRATION_READY output, transforms state,
   produces V2 output.
4. V2 chain continues from migrated state.

### Standard Contracts

- **MIGRATION_READY**: Accepts any valid computation claim. Used as
  intermediate step in migration flows.

### Contracts Without FINALIZE

Permanently locked to their current version. By design — provides
guarantees about rule stability.

## Cross-Contract Composition

**Decision**: Multi-input claims. No internal contract calls.

**Source**: E8, building on E7.

A block can claim outputs from multiple contracts simultaneously. Each
contract's spending condition is verified independently. All must pass.

### Composition Patterns

1. **Sequential pipeline**: A → B → C (each step is a different contract)
2. **Fan-in**: A + B + C → D (multiple inputs, one computation)
3. **Fan-out**: A → B + C + D (one computation, multiple outputs)
4. **Bidirectional**: Two chains sync periodically through shared blocks

| Contract | Purpose | Source |
|----------|---------|--------|
| INSURANCE | Insurance commitment on FOR collateral blocks | E2 |
| CHALLENGE | Stake-backed validity challenge | E3 |

These are conventions, not protocol primitives. Total: 8 standard

Note: the Computation contract from contracts.md is subsumed by
program-as-contract. Any WASM that exports `compute()` is a computation
contract. No separate "Computation" standard contract needed.

## Module Changes

### Sampling Module

**Changes**:
- Add `verification_cost(T)` to priority formula (dampened: `sqrt`)
- Add `chain_boost` for chain head blocks
- Report both correctness (Beta distribution) and gas utilization ratio
- Recognize computation contracts (exports `compute()`) for sample
  selection

**No changes**: Beta distribution model, pessimistic pending, core
priority formula structure.

### Gossip Module

**Changes**:
- Add contract-hash-based routing: peers advertise which computation
  contracts they serve
- Route challenge/query blocks to the publisher of the target block

**No changes**: Core gossip protocol, priority scoring.

### Consensus Module

**No changes.** Consumes weight vectors and resolves conflicts as before.
Hybrid weight (computation + economic) is computed before being passed
to consensus.

### Conflict Module

**No changes.** Computation outputs are regular outputs. Double-claims
are handled normally.

### Trust Module

**Minor addition**: Insurance commitment outputs on FOR collateral
blocks. The trust module recognizes these for self-catch flows.

### Block Creation Module

**Changes**:
- Support multi-input claims (already structurally supported)
- Auto-generate insurance commitments when publishing computation blocks
- Auto-post FOR collateral when publishing computation results

## What Is Deferred

### Oracle Logs (E1, deferred by E5)

Not needed for Phase 1–4. Most use cases work with live re-fetch for
immutable data or offline state commitments for mutable data. Add only
if real usage demonstrates the need.

### Two-Stage Commitment for Data Lookups (E1, deferred by E5)

Accept MITM risk initially. Data still gets delivered. Add commitment
scheme only if MITM becomes a real problem.

### Proxy Contracts (E8, rejected)

Indirection layers break program-as-contract, create non-deterministic
verification, and add trust chain complexity. Use explicit migration
instead.

### Internal Contract Calls (E8, rejected)

All cross-contract interaction through explicit outputs and claims.
No EVM-style internal calls. Keeps execution model simple and
dependencies visible.

**Protocol**: WASM runtime with host interface, auto-generated verify(),
computation contract execution.

**Tooling**: scaffold_sdk crate, `scaffold build`, `scaffold test`,

**Validate**: Create output → claim with correct result → verify passes.

**Tooling**: `scaffold inspect-insurance`, `scaffold devnet --deception`.

**Validate**: Publish traps, verify catch rate matches equilibrium.

### Phase 4: Offline State

**Protocol**: COMMITTED_STATE outputs, CHALLENGE/QUERY contracts,
validity lifecycle.

**Tooling**: `scaffold challenge`, SDK validate() support.

**Validate**: Challenge-response flow, aggregation with offline state.

### Phase 5: Explorer and Polish

**Protocol**: Contract-as-explorer interface (list/read/type).

**Tooling**: `scaffold explore`, `scaffold playground`.

**Validate**: Generic block explorer renders any contract's data.

## What We're NOT Building

For clarity, things explicitly excluded from this design:

1. **No governance mechanism.** No on-chain voting for parameter changes,
   contract upgrades, or dispute resolution. Markets and social
   consensus handle these.

2. **No token.** Value is abstract. The protocol tracks outputs with
   numeric values but doesn't define what the units mean.

3. **No mandatory replication.** Publishers are responsible for their
   own data availability. The protocol makes it easy to fund
   replication but doesn't require it.

4. **No block schema changes.** Everything fits in contracts and outputs
   on the existing block structure.

5. **No complex voting hierarchy.** Legacy2's 7-vote-type system is
   unnecessary. FOR/AGAINST collateral + deterministic verification
   handles everything.

| Risk | Severity | Mitigation | Source |
|------|----------|------------|--------|
| WASM floating-point non-determinism | High | Ban floats in SDK, provide fixed-point | E9 |
| Chain cascade damage | Medium | Aggregation checkpointing, chain-aware sampling | E6 |
| Weight inflation via gas overpayment | Medium | Verified weight from actual gas consumed | E7 |
| Challenge spam (DoS) | Medium | Challenger stakes collateral, rate limiting | E3, E5 |
| Computation bombs | Medium | Gas limit = declaredWeight × INSTRUCTIONS_PER_WEIGHT | E5 |
| State locked in old contracts | Low | Developer responsibility; FINALIZE mode | E8 |
| MITM re-attribution for cheap data | Low | Accept initially; add commitment if needed | E5 |
| Insurance privacy leak | None | Non-issue per E5 analysis | E2, E5 |

## Summary

The design has three pillars:

1. **Program as contract** (E4): The WASM hash IS the contract. Simple,
   powerful, fits the existing architecture perfectly.

2. **The deception game** (E2, E7): Insurance commitments + self-catch
   fund verification. The equilibrium is self-correcting and quantified.

3. **Challenge-response for offline state** (E3): Separate from queries.
   Challenged ≠ invalid. Anti-spam through challenger stakes.

Everything else supports these pillars:

- **Gas limits** (E5, E7) prevent computation bombs and make weight
  meaningful.
- **Hybrid weight** (E7) gives both computation and economic activity
  appropriate consensus influence.
- **Chain dynamics** (E6) are bounded by aggregation frequency.
- **Versioning** (E8) works through explicit migration.
- **Composition** (E8) works through multi-input claims.
- **The SDK** (E9) is thin and local-first.

The design requires NO block schema changes, NO complex voting, and NO
new protocol primitives beyond standard contracts. It builds on the
existing UTXO model, trust module, and sampling module with targeted
extensions.
