## Known gaps / deferrals

- [ ] A generator waiting on `env.claim()` is invisible to `OutputIndex` between the moment one claim resolves and the moment its `await` continuation runs, because `GenerationEnv.claim` subscribes per call rather than holding one subscription for the predicate. Two blocks ingested in the same synchronous turn therefore still spawn two generators: `GeneratorRole.trigger` sees the second output unclaimed, starts a rival, and both park on their second `claim()` with one output each -- no aggregation block is ever built. Separate turns work, so `scripts/test.ts` hides it. Fixes worth weighing: a long-lived per-predicate subscription in `GenerationEnv` that queues deliveries for the next `claim()`, or `GeneratorRole` deferring `trigger` past the current turn. Failing test in `tests/roles/GeneratorRole.test.ts` ("two blocks published in one turn are aggregated into a third")
- [ ] `OutputIndex` hands an incoming output to its subscribers in registration order, so when several in-flight generators block on the same predicate the first `claim()` to have been called wins. That is FIFO by accident, not by choice -- `GenerationJob.priority()` is `return 0`, so there is nothing to order on yet. Once profit estimation lands, the pending-claim set wants the same ordering the `ExecutionQueue` uses, or a generator with a worthless draft can starve a profitable one. Same call site as `RunQueue.dispatch`'s `// TODO: Implement this correctly`
- [ ] `PlacementService.getCanonicalAggregator` picks the sole aggregator and `todo()`s when a block has more than one. Competing aggregations are a fork (wp §6.4) and choosing between them is fork choice; anchor selection is blocked on consensus for any contested block
- [ ] Ingestion is not commutative for a block whose claim index is out of bounds, and a rejected block poisons its descendants. `ClaimIndex.propagateClaim` throws `Claim index out of bounds` only once the anchor chain is fully resolved, so the same signed block ingests fine before its anchor arrives and throws after. The throw escapes `BlockStore.ingest` with the entry left as `ingestingAtom`, so every later `get(hash)` throws -- including the `get(anchor)` inside `deserialize` of an honest child, which then poisons the child's hash too, recursively over the whole descendant cone. Remotely triggerable with one well-formed block. Failing test in `tests/graph/BlockStore.test.ts`
- [ ] `BlockStore.onIngest` keys subscriptions on the callback identity (a `Set`), so the same function reference cannot hold two independent subscriptions: the second registration is silently dropped and either signal unsubscribes both. Aborting the second signal then trips `assert(this.ingestionListeners.delete(cb))` inside an `abort` event listener, which Deno reports as an _uncatchable_ uncaught error rather than propagating to `abort()`. Unreachable today (every call site passes a fresh closure)
- [ ] Ref links never notify on ingestion. `BlockActionType` has no ref-side equivalents (`LinkRef`/`LinkReffingNode`), which `Block.refs` now needs, so a reffer and a reffed producer are never told about each other -- only claims are announced. Claim announcements are also split across two timings: `BlockIngestor.ingest` fires `LinkClaimingNode` synchronously, while `deserialize`'s BlockRef-relink path defers both sides behind a `setTimeout`. `Fetch.fetch` still works around the old gap by rescanning `payload.claims` on every `BlockStore.onIngest`, with its `LinkClaimingNode` version commented out
- [ ] `PlacementBase.place` only keeps rivals out of the _anchor's_ reach. A rival sitting inside a tree we are aggregating also orders ahead of us (wp §4.4 walks aggregates before self), and no anchor choice can fix that -- placement still returns `ok`, so the draft gets built and the aggregation eats the double-spend penalty (wp §5.3). `BlockBuilderBase.rivalClaimants` passes every rival it finds regardless of position, so `place` is where it lands today; the fix may instead be the draft dropping such claims. The refusal shape is also open: `{ok: false, tips}` means "wait for an aggregation", which never resolves this. Failing test in `tests/logic/Placement.test.ts`
- [ ] ❓ `PlacementBase.place`'s stall `tips` are a list, not a set: two stalled claims sharing an aggregation root return that root twice. Harmless until something retries a stalled build (above); decide whether `tips` is a `Set`
- [ ] `BlockStore.ingest` now asserts the deserialized atom is a `Block`, since `AtomSerializerBase.deserialize` returns `Atom` (`Block | Signal`). Unreachable today because both non-block ingestors are `UnknownIngestor` (`todo()`), but once signals are real they need either their own store or a return to a shared `AtomStore`
- [ ] `AtomSerializerBase.serialize` never asserts the allocator protocol: an ingestor that calls the allocator twice silently loses everything written to the first buffer and gets a zero-filled message signed for it, and one that never allocates dies on `undefined.set` rather than a named assert. Also `deserialize` takes `hash` from the caller and never checks it against `Hash.digest(raw)`, so a wrong hash rides along into `AtomBase` (only `BlockStore.ingest` computes it correctly today)
- [ ] The BlockRef-relink loop in `BlockIngestor.deserialize` defers its `LinkClaim`/`LinkClaimingNode` with the raw global `setTimeout` rather than `ctx.config.timeProvider.setImmediate`, so the one asynchronous edge in ingestion is invisible to the injected clock and cannot be driven deterministically from tests
- [ ] Promoting a `BlockRef` announces newly resolved `ResolvingClaim`s but silently skips `ResolvingRef`s (`claim.type === OutputResolverType.Claim` guard), because `BlockActionType` has no ref-side action. A reffer therefore never learns its ref resolved
- [ ] An aggregator cannot compute the claim indices wp §4.3 obliges it to write. `ClaimIndex.resolveClaimIndex` finds a route only by matching an _aggregation chain_ of the producer against the anchor chain, but a block being aggregated is inside the new block's own tree -- `PlacementBase.place` deliberately drops it from the anchor's coverage set, and `aggregatingNodes` cannot yet point at a block that does not exist. So every aggregation-output claim throws `No route found`. `BlockBuilderBase.build`'s mocked `anchorChain[0]` cannot help: it carries aggregates as `{block: Hash}` and is never identity-matched. resolveClaimIndex needs to search the head entry's aggregates downward. Failing test in `tests/graph/ClaimIndex.test.ts`
- [ ] `ClaimIndex.propagateClaim` accepts a negative claim index: `outputIdx < outputCount` is true for any negative value, so the claim is marked `resolved` against `outputs[-1]`. Wire claims reach it straight from `Ingestor.deserialize` and `isBlockPayload` only checks `isBigint`, so nothing else bounds them -- the upper bound is checked (`Claim index out of bounds`) but the lower one is not. `resolveClaimIndex` likewise never bounds `outputIndex` against the producer's output count, and its `parent.aggregates.findIndex(...)` silently falls back to `-1` (whole subtree) if the aggregate/aggregator links disagree. Failing test in `tests/graph/ClaimIndex.test.ts`
- [ ] `Fetch.fetch` only sees the future: it subscribes to `BlockStore.onIngest` after building its query draft, so a fetch for a predicate the node _already_ holds an answer for never calls `onResult` (wp §11.2 has clients resolving from local state; `DraftStore.onBuilt` is the codebase's own fire-if-already-satisfied idiom). Three failing tests in `tests/peer/Fetch.test.ts`
- [ ] `Fetch` open questions, not yet testable: `onResult`'s type allows `null` but nothing ever passes it, and what `null` means (no result yet / result went uncanonical) needs consensus wiring to decide; `FetchResult.parse()` resolves the raw bytes instead of running the contract's codec; and results are delivered from any ingested block with no canonicality or trust gating, so an attacker's block answers a fetch
- [ ] `Hash.toBigint` builds `new DataView(this.digest.buffer)` with no byteOffset/byteLength, so a Hash backed by a subarray of a larger buffer reads bytes 0..31 of the _backing_ buffer instead of its own 32 bytes. `toHex`/`equals`/`compare` all read the view correctly, so the same Hash reports two different values and `Hash.fromBigint(h.toBigint())` is not `h`. The module-load self-check at `src/util/Hash.ts:282` cannot catch it because `Hash.random()` always allocates a standalone buffer. Reachable: `Hash.fromBytes(env.params())` at `src/contracts/HashContract.ts:43` and `src/contracts/CollateralContract.ts:471` take caller-owned views, and `src/graph/genesis.ts:46` feeds `seed.toBigint()` into `SeededEntropyProvider`. Failing test in `tests/util/Hash.test.ts` ("BUG: toBigint respects the digest view offset")
- [ ] `Hash.add` disagrees with the rest of `Hash` about endianness: it carries from byte 0 towards byte 31 (byte 0 least significant), while `fromBigint`/`toBigint`/`compare`/`fromFraction`/`increment` all treat byte 0 as most significant. So `add(fromBigint(255n), fromBigint(1n))` is 0, not 256, and `add(x, one) !== x.increment()`. No callers yet. Failing test in `tests/util/Hash.test.ts` ("BUG: add agrees with the numeric value of the hash")
- [ ] `Hash.countLeadingZeros` scans bytes most-significant-first but scans bits within each byte least-significant-first, so it is not monotone with `Hash.compare`: `fromBigint(2n**255n)` (the largest hash) reports 7 leading zeros while the much smaller `fromBigint(2n**248n)` reports 0. That breaks the one property a leading-zero count exists for (difficulty/threshold tests). `Hash.bit(i)` uses the same mixed order (`fromBigint(1n).bit(248) === 1`, `bit(0) === 0`), so a fix should settle both at once. No callers yet. Failing test in `tests/util/Hash.test.ts` ("BUG: countLeadingZeros counts from the most significant bit")
- [ ] `arrFromNumber` shifts with `>>=`, which coerces to int32, so nothing above 2^32 survives even when 8 bytes are requested: `arrFromNumber(2**32, 8)` is all zeros. `Hash.digestParts` feeds every numeric part through `arrFromNumber(p, 8)`, so distinct values above 2^32 silently produce the same digest (`Hash.digestParts(0)` equals `Hash.digestParts(2**32)`). Values and weights are plausibly above 2^32. Failing test in `tests/util/Hash.test.ts` ("BUG: arrFromNumber encodes values above 2^32")
- [ ] `Hash.fromFraction` throws `Invalid digest length` for fractions below 2^-256 (e.g. `fromFraction(1, 1e100)`): the hex expansion is longer than 64 digits and `padEnd` does not truncate. Should saturate to zero. Low priority -- no callers. Failing test in `tests/util/Hash.test.ts` ("BUG: fromFraction handles fractions below the resolution of a hash")
- [ ] `Hash` keeps the array it is handed (`fromBytes` does not copy, `toBytes` returns the live view) but caches `hex` in the constructor, so mutating the source array afterwards leaves `toHex` and `toBytes`/`equals`/`compare` reporting different hashes -- an identity primitive that can silently change under a map key. Same aliasing surface as the `toBigint` bug above; either copy in the constructor or compute hex lazily. Documented (passing) test in `tests/util/Hash.test.ts` ("Hash: mutating the source array desynchronizes toHex from toBytes")
- [ ] Tagged JSON is not injective and its decoder is lenient. A plain object `{__t:'H'|'B'|'N', v: string}` encodes byte-identically to a genuine tagged value, so `taggedParse(taggedStringify(x))` turns it into a `Hash`/`Uint8Array`/`bigint`; any payload field literally named `__t` either gets hijacked or throws. Not exploitable today only because `blockPayloadShape` rejects unknown keys and has no free-form object fields. The decoder also accepts non-canonical bodies (`{"__t":"N","v":"0x10"}` -> 16n, `""` -> 0n, unpadded base64, uppercase hex) and ignores extra keys, so distinct wire bytes decode to the same value -- the canonical binary codec must close both. Documented (passing) tests in `tests/util/Json.test.ts`
- [ ] `mapPut`'s recursion trap deletes the key before running the mutator, so a mutator that throws destroys the entry it was meant to update rather than leaving it unchanged. Same for a throwing creator, which is fine, but the mutator path loses data. Documented (passing) test in `tests/util/collections.test.ts`
- [ ] `BaseContext` teardown edge cases: a destructor that throws aborts the rest of the teardown, skips `reset()`, and leaves the context marked destructed so it can never be torn down again (the remaining disposers leak silently); a destructor that calls `onDestruct` is silently dropped because `destruct` snapshots with `toReversed()` and `reset()` then discards the array; and `mock()` never registers a mock's `Symbol.dispose`, so a disposable mock is never disposed. Also `mapEntries` drops symbol keys even though its signature admits them. All documented (passing) tests in `tests/util/BaseContext.test.ts` / `tests/util/collections.test.ts`
- [ ] Nothing handles a deficit no ready draft can cover. `balanceFunds` returns the draft alone with `amount > 0`, and `BlockBuilderBase.checkBalanced`'s `assertEquals` throws straight out of `DraftStore.build`, leaving the draft parked in `Building` with a live retry hook. Under-funding is a normal condition, not a programmer error -- it should park like a placement stall. Worse on the retry path: the same throw escapes a `BlockStore.onIngest` listener, so one unfundable draft breaks ingestion for everyone else. Documented (passing) test in `tests/graph/DraftStore.test.ts` ("a draft nothing can fund throws out of build")
- [ ] `Config.aggregationFee` is a flat constant (default `0n`), not wp §7's two-component fee -- a flat risk term plus a term scaling with the insured throughput. At `0n` nothing built locally is worth aggregating, so the fee has to become a real computation before aggregation is exercised end to end
- [ ] Draft merging is all-or-nothing, and merging can make a block unplaceable. Two drafts whose producers sit in trees nothing has merged yet are in nobody's reach at once (wp §4.2), so no anchor covers both and `place` stalls -- taking down the primary draft, which was buildable alone, along with every draft `balanceFunds` pulled in. Adopting a ready aggregation draft can stall a block the same way. The merger needs to be able to drop a selection and retry rather than park the batch; the same fallback the rival-claimant gap below wants

## WASM contract execution (2026-08-04)

Surfaced landing `src/contract/wasm/` (manifest-blob contracts, the WasmAbi tables, three transports, unbounded worker pool). None block the current test suite.

- [ ] `ContractEnv.getResult()` is `todo()` in both envs, so the wasm `get_result` import and `blobContract` generation are wired but unusable -- both need a local blob store fed by `Scaffold.put` (also `todo()`). Until then a peer's BLOB_CONTRACT query output triggers a generation job on us that dies on `todo()` via `GenerationJob`'s `console.error` catch
- [ ] `VerificationEnv.claim()` is `todo()` and `ContractProvider.verify` has no caller at all, so wasm verification (`EnvContractProvider.verify` -> `WasmContract.run` under a `VerificationEnv`) is wired but dead code until a verification role lands; any claiming contract, wasm or TS, cannot verify even then
- [ ] `RunQueue.dispatch` launches every pending job and `FlowCtl.yield()` is empty, so `maxRunning`/`maxYielding` bound nothing. The wasm worker pool is deliberately unbounded on the strength of that bound existing -- once scheduling is implemented, at most `maxRunning + maxYielding` workers are live; today it is one worker per concurrently-admitted job
- [ ] Only the Atomics worker transport can hard-kill a guest (`worker.terminate()`). JSPI checks the signal around each blocking import but a guest suspended on a promise that never settles stays suspended forever; in-process cannot stop at all. Also `Contract.buildParams`/`walk*` carry no `FlowCtl`, so wasm walk/build invokes run unsignalled -- bounded only by ctx destruct -- and a hung walk parks its worker until then
- [ ] Fire-and-forget imports under the worker transport (`reject`, `set_result`, `debug`, the walker emits) cannot trap the guest at the faulting instruction: the host error is recorded on the main thread and thrown when the invoke settles, so a rejecting guest runs to completion first (its later `set_result`s still hit the env) before `generate`/`verify` sees the `ContractRejection`. Deliberate -- the recorded error always wins -- but a deviation from the other transports' immediate trap
- [ ] Every first use of a wasm contract whose blobs are not already in the local store mints up to two blob query blocks (manifest, then module), and the compiled `WebAssembly.Module` cache is per-`WasmContract`, so per-context. A local blob/put store would dedupe the queries and could persist compilations across contexts
- [ ] `AtomicsWorkerTransport` structured-clones `exec.arg` (the walk input / entry argument), and cloning a `Uint8Array` view copies its entire backing buffer -- params that are subarrays of a block's raw bytes drag the whole block across the thread boundary. Copy the view (`arg.slice()`) before posting if this shows up in a profile
- [ ] `WasmConfig.workerUrl` defaults to `new URL('./worker/main.ts', import.meta.url)`, which works under Deno (tests) and Vite dev (source alias) but not in production bundles: Vite only rewrites the literal `new Worker(new URL(...))` pattern, so browser builds must pass `workerUrl` (or a prebuilt worker bundle -- the stale `bundle-worker` task still points at the legacy `src/worker/worker.ts`); dnt/Node has no `Worker` global, so `'auto'` falls back to JSPI/in-process there
- [ ] `blobFetch` keeps waiting on a digest mismatch (logged `warn blobMismatch`) rather than failing, because a correct content-addressed answer may still arrive -- but that means a spoofed blob answer stalls a wasm load indefinitely instead of erroring. Revisit when block verification can reject the bad block itself

## Flood-gossip wiring (2026-08-03)

Surfaced debugging why `scripts/test.ts` blocks never reached `scripts/signalingServer.ts`.

- [x] `Gossip` was never constructed. Nothing in `src/`, `plugins/` or `scripts/` called `ctx.get(Gossip)`, and `BaseContext` only builds on demand, so its constructor -- which is the sole registration of `transport.onData`, `transport.onConnection` -> `backfill`, and `BlockStore.onIngest` -> `floodBlock` -- never ran. Both peers connected, neither ever sent a block. Fixed (2026-08-03) by `ctx.get(Gossip)` in the `Scaffold` constructor, before roles and before any transport can start
- [ ] Genesis is only ingested by `BlockBuilder.getGenesisBlock()`, so a node that never builds a block never has genesis in its `BlockStore`. The signaling server's `Gossip.backfill` therefore sends 0 blocks to every peer that connects, and it only acquired genesis because the client flooded it. Two passive peers would never converge. Genesis should be ingested during `Scaffold` construction, not lazily on first build
- [ ] `Scaffold` builds `new Context(config)` with no `EventLog`, so `ctx.logger()` returns `undefined` for every subsystem and every log call made through the public API is a no-op. `bootstrapDial`, `connectionOpened`, `backfill` and `blockSent` all already existed and would have named the bug immediately; none were reachable. `ScaffoldConfig` needs a way to supply an `EventLog` (or `Context.eventLog` needs to stop being constructor-only)
- [ ] `GossipBase.floodBlock` attributes a block to `ingestingFrom` whenever that field is set, but the field stays set for the whole synchronous fan-out of `BlockStore.ingest`. Any listener that synchronously builds and ingests a _new_ block during a remote ingest would have that new block marked as received from the sending connection and never flooded back to it. `GeneratorRole` goes through `ExecutionQueue` so nothing hits this today

## Chess contract (2026-08-11, revised 2026-08-12 for `sign`/`waitUntil`/params slots)

Surfaced porting `legacy3/demo/chess/` into `src/contract/static/chess/` and wiring `chessContract`. The rules and codec are live and tested; the contract itself cannot run yet.

- [ ] `chessContract` cannot produce a block, because `ContractEnv.send` is `todo()` in both envs. Every branch (opening, move, timeout, payout) ends in a `send`, so a chess generation job dies on `todo()` in `GenerationJob`'s `console.error` catch. Verification is dead twice over: `VerificationEnv.getResult` is `todo()`, so the action a block declares is unreadable to a verifier, and so is `claimOne` in both directions
- [ ] `signatureContract.run` is a bare `claimOne()` that never calls `env.sign(env.params())`, so any node can spend anyone's signature outputs. Chess no longer depends on this for authorization -- `env.sign` binds each move to its player directly -- but the opening block's stake claim does, and so does every change output `balanceFunds` mints. One line to fix; not done here because `GenerationEnv.sign` throws for a key the node does not hold, which may take out generation paths across the suite
- [ ] Unsettled: whether claiming an output implies that the output's predicate executes on the claiming block, or whether the claimer must declare it with `env.require`. Chess's opening block claims a `SIGNATURE_CONTRACT` output for white's stake and assumes the former. If it is the latter, that claim needs a `require`, and the same question decides how a claim of a `chess(move, ...)` output pulls in the chess execution that validates it
- [ ] No join handshake, so a match is asymmetric: the pot is white's stake alone and black risks nothing, because matching it needs both players to sign one block. This is what the params-prefix mechanism looks built for -- black publishes a stake output under a sibling predicate, and one execution reading only the shared prefix validates both claims -- so revisit once `claimAll` and multi-signer blocks exist
- [ ] The timeout is a per-move deadline, not legacy3's accumulating clock, because `waitUntil` bounds how early a block may be and nothing bounds how late. A player who misses the deadline can still move if the opponent has not yet published the timeout claim; the two blocks race for the same output and canonicality settles it. An upper-bound primitive (or exposing the block timestamp to the executing contract) would let the clock come back
- [ ] A timeout generator parks: `GenerationEnv.waitUntil` claims the match output first and then sleeps until the deadline, so on a node playing both sides -- the demo -- the opponent's parked draft holds the output the mover's own draft needs, and the local move stalls. Across nodes it is a harmless race. Deadline-derived-from-claim ordering is forced (the deadline comes from `claimed.blockTimestampMs`), so the fix belongs in draft scheduling, not the contract
- [ ] `chessContract` supplies no `walkData`, because a chess output's data has three shapes with nothing to discriminate them: the state (on the value-carrying output), the seed naming both players, and the action (both on amount-0 self-claimed result outputs). A host walking a chess output cannot tell which it holds. Either the result outputs need their own params slot or `walkData` needs the output's predicate, not just its bytes
- [ ] Two classes mean "this block is invalid": `ContractRejection` (thrown by the wasm path) and `VerificationFailure` (the only one `EnvContractProvider.verify` catches). `chessContract` throws `VerificationFailure` to land on the catching path, while `blobContract` and `exactBlockContract` throw plain `Error`s that `verify` re-throws as a hard error instead of returning an invalid verdict. Settle on one class and make both providers catch it
