## Known gaps / deferrals

- [ ] Block codec is tagged JSON (`taggedStringify`/`taggedParse`), which is value-stable but not byte-stable: decoding then re-encoding a received block generally yields different bytes, hence a different hash. `raw` is therefore the only source of block identity -- never rebuild wire bytes from a decoded payload. Replace with a canonical binary codec, then assert `encode(decode(raw)) === raw` at ingestion (wp 4.1)
- [ ] Ingestion error handling at the funnel edge: `BlockIngestor.deserialize` throws on malformed input and nothing catches it, so no warn is logged for bad peer data (AGENTS.md). Also `AtomStore.ingest` marks the hash `ingestingAtom` before deserializing, so a throw leaves the entry poisoned forever -- later `get(hash)` throws "Cannot get an ingesting fact!" rather than reporting a known-bad atom
- [ ] Canonicality recompute is O(N) in v0; incremental O(log N) later (the interface must allow the swap)
- [ ] Delete `src/core/CoreContext.ts` (dead stub) when cutting over old code
- [ ] docs/v2/scaffold.md is still empty; fill once the facade API firms up
- [ ] `PlacementService.getCanonicalAggregator` picks the sole aggregator and `todo()`s when a block has more than one. Competing aggregations are a fork (wp §6.4) and choosing between them is fork choice; anchor selection is blocked on consensus for any contested block
- [ ] Nothing retries a stalled build. `BlockBuilderModule.build` parks the draft in `currentBuild: 'pending_aggregation'` and returns the tips, but subscribing to those tips' `listeners` and re-running the build is reactive-layer work that doesn't exist yet
- [ ] Anchor selection needs the full anchor chain in memory: a candidate whose chain hits a `BlockRef` is dropped, because an unresolved link can hide an exclude. That conflicts with wp §3.3's "most blocks are expected to be forgotten" -- a light client that forgot its anchor chain can't place at all. Either placement fetches on demand, or reach has to be provable from an O(log N) path
- [ ] Placement prefers the tightest covering anchor (the freshest block that still reaches everything). That assumes the loose reading of wp §4.2's "larger tree" constraint; under a strict reading a fresh leaf could never anchor at another fresh leaf, and the preference would have to invert. Ties into the "size" decision above
- [ ] Ingestion is not commutative for a block whose claim index is out of bounds, and a rejected block poisons its descendants. `ClaimIndexService.propagateClaim` throws `Claim index out of bounds` only once the anchor chain is fully resolved, so the same signed block ingests fine before its anchor arrives and throws after. The throw escapes `BlockStore.ingest` with the entry left as `ingestingAtom`, so every later `get(hash)` throws -- including the `get(anchor)` inside `deserialize` of an honest child, which then poisons the child's hash too, recursively over the whole descendant cone. Remotely triggerable with one well-formed block. Failing test in `tests/BlockStore.test.ts`
- [ ] `BlockStore.onIngest` keys subscriptions on the callback identity (a `Set`), so the same function reference cannot hold two independent subscriptions: the second registration is silently dropped and either signal unsubscribes both. Aborting the second signal then trips `assert(this.ingestionListeners.delete(cb))` inside an `abort` event listener, which Deno reports as an *uncatchable* uncaught error rather than propagating to `abort()`. Unreachable today (every call site passes a fresh closure)
- [ ] Ref links never notify on ingestion. `BlockActionType` has no ref-side equivalents (`LinkRef`/`LinkReffingNode`), which `Block.refs` now needs, so a reffer and a reffed producer are never told about each other -- only claims are announced. Claim announcements are also split across two timings: `BlockIngestor.ingest` fires `LinkClaimingNode` synchronously, while `deserialize`'s BlockRef-relink path defers both sides behind a `setTimeout`. `FetchService.fetch` still works around the old gap by rescanning `payload.claims` on every `BlockStore.onIngest`, with its `LinkClaimingNode` version commented out
- [ ] `PlacementModule.place` only keeps rivals out of the *anchor's* reach. A rival sitting inside a tree we are aggregating also orders ahead of us (wp §4.4 walks aggregates before self), and no anchor choice can fix that -- placement still returns `ok`, so the draft gets built and the aggregation eats the double-spend penalty (wp §5.3). `BlockBuilderModule.rivalClaimants` passes every rival it finds regardless of position, so `place` is where it lands today; the fix may instead be the draft dropping such claims. The refusal shape is also open: `{ok: false, tips}` means "wait for an aggregation", which never resolves this. Failing test in `tests/Placement2.test.ts`
- [ ] ❓ `PlacementModule.place`'s stall `tips` are a list, not a set: two stalled claims sharing an aggregation root return that root twice. Harmless until something retries a stalled build (above); decide whether `tips` is a `Set`
- [ ] `BlockStore.ingest` now asserts the deserialized atom is a `Block`, since `AtomSerializerModule.deserialize` returns `Atom` (`Block | Signal`). Unreachable today because both non-block ingestors are `UnknownIngestor` (`todo()`), but once signals are real they need either their own store or a return to a shared `AtomStore`
- [ ] `AtomSerializerModule.serialize` never asserts the allocator protocol: an ingestor that calls the allocator twice silently loses everything written to the first buffer and gets a zero-filled message signed for it, and one that never allocates dies on `undefined.set` rather than a named assert. Also `deserialize` takes `hash` from the caller and never checks it against `Hash.digest(raw)`, so a wrong hash rides along into `AtomBase` (only `BlockStore.ingest` computes it correctly today)
- [ ] The BlockRef-relink loop in `BlockIngestor.deserialize` defers its `LinkClaim`/`LinkClaimingNode` with the raw global `setTimeout` rather than `ctx.config.timeProvider.setImmediate`, so the one asynchronous edge in ingestion is invisible to the injected clock and cannot be driven deterministically from tests
- [ ] Promoting a `BlockRef` announces newly resolved `ResolvingClaim`s but silently skips `ResolvingRef`s (`claim.type === OutputResolverType.Claim` guard), because `BlockActionType` has no ref-side action. A reffer therefore never learns its ref resolved
- [ ] An aggregator cannot compute the claim indices wp §4.3 obliges it to write. `ClaimIndexService.resolveClaimIndex` finds a route only by matching an *aggregation chain* of the producer against the anchor chain, but a block being aggregated is inside the new block's own tree -- `PlacementModule.place` deliberately drops it from the anchor's coverage set, and `aggregatingNodes` cannot yet point at a block that does not exist. So every aggregation-output claim throws `No route found`. `BlockBuilderModule.build`'s mocked `anchorChain[0]` cannot help: it carries aggregates as `{block: Hash}` and is never identity-matched. resolveClaimIndex needs to search the head entry's aggregates downward. Failing test in `tests/ClaimIndex.test.ts`
- [ ] `ClaimIndexService.propagateClaim` accepts a negative claim index: `outputIdx < outputCount` is true for any negative value, so the claim is marked `resolved` against `outputs[-1]`. Wire claims reach it straight from `Ingestor.deserialize` and `isBlockPayload` only checks `isBigint`, so nothing else bounds them -- the upper bound is checked (`Claim index out of bounds`) but the lower one is not. `resolveClaimIndex` likewise never bounds `outputIndex` against the producer's output count, and its `parent.aggregates.findIndex(...)` silently falls back to `-1` (whole subtree) if the aggregate/aggregator links disagree. Failing test in `tests/ClaimIndex.test.ts`
- [ ] `FetchService.fetch` only sees the future: it subscribes to `BlockStore.onIngest` after building its query draft, so a fetch for a predicate the node *already* holds an answer for never calls `onResult` (wp §11.2 has clients resolving from local state; `DraftStore.onBuilt` is the codebase's own fire-if-already-satisfied idiom). Two smaller leaks alongside it: an already-aborted `input.signal` still creates and builds the draft, publishing a query output for a request the caller abandoned; and aborting later unsubscribes the ingest listener but never calls `DraftStore.cancel`, so a build stalled on placement keeps retrying forever. Three failing tests in `tests/FetchService.test.ts`
- [ ] `FetchService` open questions, not yet testable: `onResult`'s type allows `null` but nothing ever passes it, and what `null` means (no result yet / result went uncanonical) needs consensus wiring to decide; `FetchResult.parse()` resolves the raw bytes instead of running the contract's codec; and results are delivered from any ingested block with no canonicality or trust gating, so an attacker's block answers a fetch
- [ ] `Hash.toBigint` builds `new DataView(this.digest.buffer)` with no byteOffset/byteLength, so a Hash backed by a subarray of a larger buffer reads bytes 0..31 of the *backing* buffer instead of its own 32 bytes. `toHex`/`equals`/`compare` all read the view correctly, so the same Hash reports two different values and `Hash.fromBigint(h.toBigint())` is not `h`. The module-load self-check at `src/util/Hash.ts:282` cannot catch it because `Hash.random()` always allocates a standalone buffer. Reachable: `Hash.fromBytes(env.params())` at `src/contracts/HashContract.ts:43` and `src/contracts/CollateralContract.ts:471` take caller-owned views, and `src/genesis.ts:46` feeds `seed.toBigint()` into `SeededEntropyProvider`. Failing test in `tests/Hash.test.ts` ("BUG: toBigint respects the digest view offset")
- [ ] `Hash.add` disagrees with the rest of `Hash` about endianness: it carries from byte 0 towards byte 31 (byte 0 least significant), while `fromBigint`/`toBigint`/`compare`/`fromFraction`/`increment` all treat byte 0 as most significant. So `add(fromBigint(255n), fromBigint(1n))` is 0, not 256, and `add(x, one) !== x.increment()`. No callers yet. Failing test in `tests/Hash.test.ts` ("BUG: add agrees with the numeric value of the hash")
- [ ] `Hash.countLeadingZeros` scans bytes most-significant-first but scans bits within each byte least-significant-first, so it is not monotone with `Hash.compare`: `fromBigint(2n**255n)` (the largest hash) reports 7 leading zeros while the much smaller `fromBigint(2n**248n)` reports 0. That breaks the one property a leading-zero count exists for (difficulty/threshold tests). `Hash.bit(i)` uses the same mixed order (`fromBigint(1n).bit(248) === 1`, `bit(0) === 0`), so a fix should settle both at once. No callers yet. Failing test in `tests/Hash.test.ts` ("BUG: countLeadingZeros counts from the most significant bit")
- [ ] `arrFromNumber` shifts with `>>=`, which coerces to int32, so nothing above 2^32 survives even when 8 bytes are requested: `arrFromNumber(2**32, 8)` is all zeros. `Hash.digestParts` feeds every numeric part through `arrFromNumber(p, 8)`, so distinct values above 2^32 silently produce the same digest (`Hash.digestParts(0)` equals `Hash.digestParts(2**32)`). Values and weights are plausibly above 2^32. Failing test in `tests/Hash.test.ts` ("BUG: arrFromNumber encodes values above 2^32")
- [ ] `Hash.fromFraction` throws `Invalid digest length` for fractions below 2^-256 (e.g. `fromFraction(1, 1e100)`): the hex expansion is longer than 64 digits and `padEnd` does not truncate. Should saturate to zero. Low priority -- no callers. Failing test in `tests/Hash.test.ts` ("BUG: fromFraction handles fractions below the resolution of a hash")
- [ ] `Hash` keeps the array it is handed (`fromBytes` does not copy, `toBytes` returns the live view) but caches `hex` in the constructor, so mutating the source array afterwards leaves `toHex` and `toBytes`/`equals`/`compare` reporting different hashes -- an identity primitive that can silently change under a map key. Same aliasing surface as the `toBigint` bug above; either copy in the constructor or compute hex lazily. Documented (passing) test in `tests/Hash.test.ts` ("Hash: mutating the source array desynchronizes toHex from toBytes")
- [ ] Tagged JSON is not injective and its decoder is lenient. A plain object `{__t:'H'|'B'|'N', v: string}` encodes byte-identically to a genuine tagged value, so `taggedParse(taggedStringify(x))` turns it into a `Hash`/`Uint8Array`/`bigint`; any payload field literally named `__t` either gets hijacked or throws. Not exploitable today only because `blockPayloadShape` rejects unknown keys and has no free-form object fields. The decoder also accepts non-canonical bodies (`{"__t":"N","v":"0x10"}` -> 16n, `""` -> 0n, unpadded base64, uppercase hex) and ignores extra keys, so distinct wire bytes decode to the same value -- the canonical binary codec must close both. Documented (passing) tests in `tests/Json.test.ts`
- [ ] `mapPut`'s recursion trap deletes the key before running the mutator, so a mutator that throws destroys the entry it was meant to update rather than leaving it unchanged. Same for a throwing creator, which is fine, but the mutator path loses data. Documented (passing) test in `tests/UtilCollections.test.ts`
- [ ] `BaseContext` teardown edge cases: a destructor that throws aborts the rest of the teardown, skips `reset()`, and leaves the context marked destructed so it can never be torn down again (the remaining disposers leak silently); a destructor that calls `onDestruct` is silently dropped because `destruct` snapshots with `toReversed()` and `reset()` then discards the array; and `mock()` never registers a mock's `Symbol.dispose`, so a disposable mock is never disposed. Also `mapEntries` drops symbol keys even though its signature admits them. All documented (passing) tests in `tests/BaseContext.test.ts` / `tests/UtilCollections.test.ts`
- [ ] Nothing handles a deficit no ready draft can cover. `balanceFunds` returns the draft alone with `amount > 0`, and `BlockBuilderModule.checkBalanced`'s `assertEquals` throws straight out of `DraftStore.build`, leaving the draft parked in `Building` with a live retry hook. Under-funding is a normal condition, not a programmer error -- it should park like a placement stall. Worse on the retry path: the same throw escapes a `BlockStore.onIngest` listener, so one unfundable draft breaks ingestion for everyone else. Documented (passing) test in `tests/DraftStore.test.ts` ("a draft nothing can fund throws out of build")
- [ ] `Config.SIGNATURE_CONTRACT_HASH` (`Hash.digest('signature')`) names no registered contract -- `DefaultContractProvider` routes only `demo`, so the change outputs `balanceFunds` mints and `ExecutionModule`'s store-of-value check are both keyed on a hash nothing can execute. It also disagrees with v1's `SIGNATURE_CONTRACT = Hash.digest('signature-contract')` in `src/core/Block.ts`; settle on one before `src/contracts/SignatureContract.ts` is wired up
