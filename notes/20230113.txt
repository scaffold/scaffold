requiring TIME t is saying that timestamp > t

Only allow UNIQUE <verifier, timestamp> pairs in the graph.

The canonical answer to a verifier is the one with the earliest timestamp.
  Tough to prevent something being generated and passed as something retrieved from storage.

Although answers aren't unique per verifier, UTXOs are.
  If a contract says that an input from verifier V MUST consume 1 coin, then any answer is unmergable with another answer.
  If the input's verifier enforces a similar restriction, and this happens recursively, then only 1 chain is ever allowed.

Do we incentivize via incentives or bids?
  I think we start with incentives since we'll always need that.
  To use an input, it MUST output to your verifier.
    Young blocks can be re-written to add the output, but older blocks will need to be wrapped.
  We also need to get the block secret from the publishing peer.
    Requiring secret from inputs means that stealing a block requires at least the time it takes to get the secret.
      We want to slow down block robbers but not authentic authors.
    What happens when I output to a verifier, but then refuse to provide the secret?
      My block will never be mergable.
